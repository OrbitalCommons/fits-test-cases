**Description**: A small legacy (pre-MWAX) gpubox file for observation 1196175296 (ForA, 2017-12-01): two timesteps (`MILLITIM` 0 and 500, `INTTIME = 0.5`) of two fine channels each, as two tile-compressed `float64` images. Per Birli's `tests/data/README.md` it is a synthetic observation written with astropy by Birli's `generate_test_data.py`, based on the real observation but limited to two coarse channels, two batches, two scans per batch and two fine channels per coarse channel, and filled with unique values that increase with their position in the file. astropy decodes HDU 1 as 0, 1, 2, … 132095 and HDU 2 as 262144 + the same index, row-major.

The compressed headers say `ZCMPTYPE = 'RICE_1'` and `ZBITPIX = -64` with `NOISEBIT = 16`, but every tile's `COMPRESSED_DATA` cell is empty (`1PB(0)`) and the data are in the `GZIP_COMPRESSED_DATA` column: the lossless gzip fallback for float tiles that cannot be quantized. The `ZSCALE` and `ZZERO` columns are present and 0 in every row.

**Instrument/Mission**: Murchison Widefield Array (MWA), legacy correlator

## FITS Features Exercised

- Tile-compressed `float64` images whose tiles all use the `GZIP_COMPRESSED_DATA` fallback under a `RICE_1` header
- Partial reads of a compressed image: `read_section` and `read_rows` of single tile rows and of the last row ([fitsio-pure#147](https://github.com/OrbitalCommons/fitsio-pure/issues/147)); the counter values make a wrong window obvious
- Into-buffer reads of a compressed float image ([fitsio-pure#146](https://github.com/OrbitalCommons/fitsio-pure/issues/146))
- Two HDUs with the same `EXTNAME` (`COMPRESSED_IMAGE`) and no `EXTVER`; fitsverify warns that they are identical in type and name
- Numeric header cards read as strings: `FINECHAN = 640.0`, `INTTIME = 0.5` ([fitsio-pure#143](https://github.com/OrbitalCommons/fitsio-pure/issues/143))
